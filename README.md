# Habitat

**一个以文件为事实源的个人知识库与工作台。** 自托管，Markdown 可读可迁移，事件流可审计，SQLite 只当索引——
你的笔记永远是硬盘上的 `.md`，删掉这个程序也照样能读。

```
┌──────────┐   ┌──────────┐   ┌──────────┐
│  .md 文件 │ → │  事件流   │ → │  SQLite  │
│  事实源   │   │  审计/撤销 │   │  只读索引 │
└──────────┘   └──────────┘   └──────────┘
```

## 为什么做这个

大多数笔记工具解决的是「怎么记」，很少有人管**记完之后**：

1. **数据被锁在别人的数据库里**。导出是一堆 ID 和外键，迁不走。
2. **AI 只能读，不能安全地写**。让它整理，它直接改文件，改错了你也不知道哪一次、为什么。
3. **没人维护就会烂成垃圾箱**。三个月不看，收件箱 200 条，笔记互相不认识。

这三件事各有对应的设计决定（见下）。目标不是做一个更好的编辑器，是做一个**可以交给 Agent 长期维护、同时你还敢信**的存储层。

## 三个设计决定

### 1. 文件是唯一事实源，索引是可丢弃的

所有内容都是 Markdown + YAML frontmatter，按目录组织。SQLite 里只有检索索引和派生缓存——
删掉 `.habitat/state/*.db`，重启会从文件重建，一条不丢。

换来的是：`git` 能管、脚本能批量处理、十年后换个工具照样读得懂。

### 2. 所有写入都是一次事务

没有「直接改文件」这条快捷方式（人可以用编辑器改，但要补一条账）。每次修改都走：

```
propose（带基准）→ validate（四项校验）→ commit（落盘 + 事件 + 反向操作）
```

- **基准**：提交时带上「我看到的是哪一版」，别人抢先改过就给你三方对比，不覆盖。
- **事件**：谁、什么时候、改了什么、为什么，全部留痕。
- **反向操作**：每次提交都能整批撤销。

这就是为什么敢让 AI 写：它只能 `propose`，改语义要人确认，一天配额默认 3 次，超额直接 429。

### 3. 状态是算出来的，不是手填的

对象处在生命周期的哪一步（已采集 → 已判断 → 已成篇 → 已接入 → 已定稿），
是由事实推导的（正文长度、有没有双链、有没有定稿标记），不是一个你懒得维护的标签字段。

另外有一条**与成熟度正交的活性轴**：多久没人碰。两者合起来才能回答
「这条还成立吗」和「还有人在用吗」——只有前者会得到「状态很好但已经死了」的库。

## 30 秒跑起来

```bash
git clone <this-repo> && cd habitat
npm install

# 造一个空空间（也可以指向你已有的 Markdown 目录）
npm run setup

npm run dev          # 前端 5178，后端 8787
```

打开 http://127.0.0.1:5178 。`npm run setup` 会在 `./space` 建一个最小可用的示例空间。

```bash
npx habitat status    # 空间概览
npx habitat search "关键词"
```

> 需要 Node 22+（`better-sqlite3` 是原生模块，换大版本要 `npm rebuild`）。

## 每天怎么用

三种入口，走的是同一套写入路径，互相不打架：

| 入口 | 适合 |
|---|---|
| **网页** https://你的域名 | 读、写、看板、阅读器、变更对比 |
| **CLI** `habitat …` | 脚本、定时任务、任意 Agent harness |
| **MCP** `habitat mcp` | Claude Desktop / Cursor / 任何支持 MCP 的客户端 |

### 常用命令

```bash
habitat status                     # 空间概览 + 链接解析率
habitat search "关键词"             # 中文 2-gram 检索
habitat capture "标题" --body "…"   # 采集 → 收件箱
habitat task "写 spec" --due 2026-11-02 --project <id>
habitat event "开会" --date 2026-11-03 --start 14:00
habitat attach ./收据.png           # 附件入库，返回可插入的 markdown

habitat brief                      # 今日简报：今天/逾期/读一半/积压/断链
habitat next                       # AI 该接手什么
habitat refresh                    # 哪些东西冷掉了
habitat renew <id>                 # 翻新证据包：它主张什么 + 哪几条可能撞上
habitat review <id> --ok           # 确认仍成立 → 间隔往后推
```

### 交给 Agent 维护

任何能跑命令的 harness，进来先跑一句 `habitat brief` 就知道现状。
`habitat next` 会给出带 id 的、**有明确 AI 切入点**的清单（判断 / 提炼 / 连接 / 质疑四类）。

不配 Agent 的时候系统也能自己转：服务内置代谢（归档已完成、发简报、到点提醒），
只是不做语义判断——那是留给人和 AI 的。

## 架构

```
server/
  core/       存储、变更、事件、索引、生命周期、翻新、提醒、邮件、附件
  routes/     HTTP API（一个文件，按域分段）
  mcp.ts      MCP 服务（stdio）
shared/       前后端共用：类型、frontmatter、生命周期模型
src/           React 界面，按域拆（actions / library / changes / system …）
```

- [`docs/architecture.md`](docs/architecture.md) — 数据模型、写入路径、并发与冲突、索引重建
- [`docs/lifecycle.md`](docs/lifecycle.md) — 生命周期模型、活性与翻新机制

## 安全与隐私

- **数据不出机器**。默认只监听 `127.0.0.1`；要公网访问自己配隧道 + 令牌。
- **凭据不进仓库**。`.env`、`mail.json`、`remote.json` 都在 `.gitignore` 里，
  SMTP 密码/授权码存在 `~/.habitat/mail.json`，不放在数据目录（数据目录常被同步到云盘）。
- **令牌**通过 `KB_TOKEN` 环境变量注入，不写进命令行、不写进文件。
- **不删除，只归档**。归档写 `[archived:: 时间]` 标记，文件还在。
- **原件只读**。带 `source` 的章节和 `assets/originals/` 下的文件不可改。

## 测试

```bash
npm run typecheck     # 严格模式
npm run test:unit     # 57 条：扫描、变更、索引、生命周期、翻新、邮件
npm run test:e2e      # 76 条：真浏览器跑完整流程
```

E2E 在仓库内的 `.e2e-space` 里跑，每次重建，不碰你的真实数据。

## 现状与局限（说实话）

- **没有内建模型**。助手是规则式检索 + 模板；「AI 判断」全部由外部 harness 完成，服务端只做确定性的事。
- **单机单进程**。SQLite + 文件锁，适合一个人一台机器；多人协作没做。
- **只在本机活着时工作**。关机就停，提醒和简报那段时间不会补跑。
- **单空间**。一个进程一个空间，没有多租户与权限分级。
- **召回靠词面**。中文二元组 + Jaccard，同义改写抓不到；换成 embedding 会更好，但会引入依赖。
