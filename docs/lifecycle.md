# 生命周期模型

## 为什么需要它

一个知识库如果只回答「东西存在哪」，不回答**「它现在处在哪一步、下一步该做什么、谁能推」**，
那它迟早变成一个垃圾桶：东西都在，但没人知道该拿它们怎么办。

更糟的是 AI 也用不上——你只能说「帮我整理一下」，它只能瞎猜。有了显式状态机，AI 才有确定的切入点。

## 三条流

不同对象走不同的路，不共用一个状态词表：

| 流 | 覆盖 | 一句话目标 |
|---|---|---|
| **知识** | 碎片 / 笔记 | 从「收进来了」到「可以被引用」 |
| **行动** | 任务 / 项目 | 从「待办」到「完成且归档」 |
| **材料** | 书 / 章节 / 载体 | 从「原件在」到「消化成自己的结论」 |

`已归档` 是**跨流终态**。归档写 `[archived:: 时间]`，不删文件。

> 这里踩过一个坑：归档状态最初只定义在「行动」流里，知识和材料流没有，
> 于是它们落到兜底分支「第一个状态」——表现为**归档过的笔记又活过来了**。
> 状态机必须显式穷举终态，不能靠 fallback。

## 每个状态必须回答四件事

少一样就不许定义：

| 要素 | 例子（知识流的「已判断」） |
|---|---|
| **意义** | 知道它是什么、值不值得留 |
| **可去** | → 已成篇 / 已归档 |
| **谁能推** | 人 / AI |
| **产出** | 正文 + 至少一条出链 |
| **AI 钩子** | 提炼：压成自己的话，指出和哪条相关或冲突 |

## 状态机

### 知识

```
已采集 ──→ 已判断 ──→ 已成篇 ──→ 已接入 ──→ 已定稿 ──→ 被取代
  │          │           │           │           │
  └──────────┴───────────┴───────────┴───────────┴──→ 已归档
```

判定规则（确定性，不看感觉）：

| 状态 | 判据 |
|---|---|
| 已成篇 | 正文 ≥ 200 字 |
| 已接入 | 有任一双链（出链或入链） |
| 已定稿 | `status: evergreen` |
| 被取代 | 有 `supersededBy` |

### 行动

```
待办 ──→ 进行中 ──→ 已完成 ──→ 已归档
  └──────────────────────────┘
```

`已完成 → 已归档` 可以**由定时器推**（默认 30 天），其余必须人推。

### 材料

沿用五段闸门：已入库 → 有衍生 → 已消化 → 回顾过 → 已沉淀。

外加一个终态 **备查**（`status: reference`）：不打算逐章消化、留作查阅的书。

没有它，一本参考手册会永远显示成「没消化」，永远算欠账——4 本书 43 章挂在「已入库」上，
其中可能只有 1-2 本是真的要读的。把「不打算读」和「还没读」分开，数字才有意义。

## 控制流：谁能推什么

| 触发者 | 能做什么 | 不能做什么 |
|---|---|---|
| **人** | 任何转移 | — |
| **AI** | 只能 `propose`；改语义要人确认；日配额默认 3 条变更集，超额 429 | 删、跳闸门、改原件 |
| **定时器** | 时间投影：逾期、已完成 30 天归档、提醒、简报 | 任何语义判断 |
| **外部（文件/邮件）** | 落文件、投邮件 → 进收件箱 | 直接改已有对象 |

## 数据流：一次转移产出四样

```
文件（事实源） + 事件（可审计） + 派生（索引/双链/简报） + 反向操作（可撤销）
```

缺任何一样都会出问题：没有文件等于没发生；没有事件无法追溯；没有派生界面看不到；
没有反向操作，谁都不敢让 AI 批量干活。

## 使用：与成熟度正交的第二维

只算成熟度会出现「已定稿但三年没人看」——状态很漂亮，实际已经死了。

所以记录五个使用通道：

| 通道 | 何时记 |
|---|---|
| `open` | 打开阅读器 / 编辑器 |
| `read` | 阅读进度上报 |
| `search` | 检索命中 |
| `edit` | 提交变更 |
| `ai` | CLI / MCP 读取 |

落在 `.habitat/state/usage.json`，**不写 journal**——打开一次就写一条事件，一天几百条，
真正重要的「谁改了什么」会被噪音淹掉。

活性分档：**活跃 7 天 / 常温 30 天 / 转冷 90 天 / 冰冷 180 天 / 灰**。

## 翻新：把「该翻新」变成「有证据可判」

只提醒「你有 48 条 200 天没动」是没用的，人会直接关掉。

借鉴 Obsidian 的 *Contradiction Finder*：它用 **embedding 召回 + LLM 判定**两段式，
核心洞察是**召回便宜、判定贵**，所以限制 LLM 调用次数。

这套系统没有模型，所以拆成：

- **服务端做召回**（确定性）：BM25 检索 + 中文二元组词袋 Jaccard，
  排序按「比自己新的优先 → 含转折词 → 相似度」。输出候选，不下结论。
- **harness 做判定**：读证据包，决定要不要 `supersededBy`。

```
due → 挑一条 → renew 拿证据包
   ├─ 候选里有真冲突 → superseded 提案（旧文不删）
   └─ 没有冲突       → review --ok，间隔推一档
```

间隔用固定阶梯 **1 / 3 / 7 / 21 / 60 / 180 天**，不用 SM-2 的难度因子
（社区叫「ease hell」：老判难会让卡片永远高频出现，人很快就烦了）。

`due` 默认一次只给 5 条——社区反复踩过的坑是「一次导入几百条，一周后堆成山，直接放弃」。

## AI 的四个切入点

| 切入点 | 在哪个状态 | 输入 → 输出 |
|---|---|---|
| **判断** | 已采集 | 碎片 + 标签分布 → 标签 / 归属 / 去重建议 |
| **提炼** | 已判断、有衍生 | 原文 + 相关条目 → 摘要 / 批注 / 衍生 |
| **连接** | 已成篇 | 当前笔记 + 候选 → 双链建议 |
| **质疑** | 已接入、已定稿 | 旧结论 + 新证据 → `supersededBy` 提案 |

入口：`habitat next` / `habitat stuck --ai` / `habitat state <id>`。

## 什么算「欠账」

这一条踩过坑，值得单独写。

最初 `stuck` = 所有非终态对象，简报直接把**状态分布**当卡点报，于是出现过
「52 篇卡住」——而其中 46 篇是写了完整结论的 `growing` 笔记，只是没人去改 `evergreen` 标签。

那种数字看三天，人就会学会忽略它，然后真正卡住的也一起被忽略。

现在分两类：

| 类别 | 判据 | 出现在哪 |
|---|---|---|
| **真欠账** | 有明确的缺口：没结论、没双链、正文不足、材料没有任何衍生 | 简报「真欠账」+ `habitat next` |
| **稳定态** | 接入态 + 正文有「结论/判断/要点」小节 = 内容完整，只差一次确认 | 简报「稳定态」，每周抽几篇过一遍 |

判「有没有结论」只认**小节标题**，不做全文关键词扫描——正文里讨论 TODO 的笔记太多，
用关键词会把引用源码的段落全判成没写完（实测 14 篇误报里 12 篇是这个原因）。

## 已知缺口

1. **判定是启发式的**（200 字算「成篇」是拍的，不是测出来的）。
2. **只有三条流**，专题、批注、提案还没纳入状态机。
3. **AI 钩子仍是「备料」，不是「代劳」**：`habitat next` / `loops run` 给出的是带 id 的工单，
   真正的判断由模型或人做，做完用 `habitat loops beat <id> --produced …` 交账。
   系统不替模型下结论，但也因此必须靠回执来判断「有没有人接」——没有回执就是没接。
4. **召回靠词面不靠语义**，同义改写抓不到。
5. **衰减参数没有实证**，用满半年后应该按真实回流率调。
