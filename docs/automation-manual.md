# 自动化闭环参考手册

> 这份手册由 `habitat loops manual` 从闭环目录生成。不要手改；改 `shared/loops.ts` 后重新生成。

生成时间：2026-11-04T14:34:45+08:00

## 0. 先读这一页

一个闭环要成立，必须同时有六样东西：**触发、入口、步骤、产物、证据、降级**。
缺任何一样，它就会变成「文档里写了、实际没人跑」的空壳。这份手册逐条列出来，就是为了让缺口看得见。

三种角色，三条读法：

| 角色 | 先看 | 然后 |
|---|---|---|
| 人 | `habitat loops status` | 只看 `down` / `blocked` / 积压最大的三条 |
| 平台 Agent | `GET /api/loops` | 按 `owner` 跑，跑完 `beat`，产物写进 `produced` |
| 外部 harness | `habitat loops list --json` | `bind --harness profile.yaml` 看能接哪些，生成 cron，跑完 beat |

## 1. 状态怎么判

| 状态 | 含义 | 该做什么 |
|---|---|---|
| `ok` | 最近一次回执在上限内 | 不用管 |
| `late` | 超过上限但不到两倍 | 看一眼是不是调度器漏了一轮 |
| `down` | 超过两倍，或上次失败 | 立刻处理：这是真正的空壳 |
| `never` | 从未留下回执 | 先确认是「刚部署」还是「根本没接」 |
| `blocked` | 缺依赖（邮件 / IMAP） | 补配置，或明确接受降级 |
| `paused` | 被显式停用 | 确认是谁停的、为什么 |
| `manual` | 按需 / 事件型，不做存活判定 | 看 backlog |

`maxSilenceMinutes` 是容忍上限，默认按「两倍」判 down，留了一次漏跑的余量。

## 2.1 维持（7 条）

不需要判断力，必须自己转。人不在、模型不在，它们也应该照常工作。

### 1. `watch-external` 外部改动入索引

**目标**：文件被编辑器或脚本改过之后，索引和界面自己看见，不靠人手动刷新。

| 项 | 值 |
|---|---|
| 触发 | 每 15 秒 |
| 模式 | 自动 · 自主度 可写派生 |
| 执行者 | 服务端 |
| 存活上限 | 1 小时 |

**入口**：`habitat reindex` ｜ `POST /api/system/rescan` ｜ UI：系统 · 健康恢复

**步骤**：
1. 比对 (mtime,size) 指纹
2. 只重解析变过的文件
3. 同步索引里动过的对象
4. 前端轮询自然看到

**产物**：索引更新（不产生内容变更）

**证据**：receipt.counts.objects/links；/api/system → health.indexDocs

**幂等**：天然幂等：按当前指纹重算，不依赖「上次跑到哪」

**降级**：
- 没有调度器 → 只在打开页面或手动 rescan 时同步，外部改动会晚一点出现

**默认归属**：平台进程

> 这是 level-triggered 的典型：漏掉一轮没关系，下一轮看的是当前状态。


### 2. `reconcile` 对账

**目标**：把「谁改的」说清楚：外部改动记成 external_edit，可认领，不覆盖。

| 项 | 值 |
|---|---|
| 触发 | 事件：人工 / harness 触发，建议每日一次 |
| 模式 | 自动 · 自主度 可写派生 |
| 执行者 | 服务端 / 外部 harness / 人 |
| 存活上限 | 2 天 |

**入口**：`habitat agent reconcile` ｜ `POST /api/agent/reconcile` ｜ UI：接入 · 事件流

**步骤**：
1. 读基线快照 sha256
2. 逐文件比对
3. 未署名改动 → external_edit 事件
4. 首次运行只建基线

**产物**：external_edit / reconcile 事件

**证据**：receipt.counts.added/removed/changed/unsigned；journal

**幂等**：按快照差分；同一改动不会重复记账

**降级**：
- 没有调度器 → 只能人工在接入页点一次

**默认归属**：harness 或平台


### 3. `metabolism` 代谢归档

**目标**：已完成超过 30 天的任务自动归档——不删文件，只打标记，可整批撤销。

| 项 | 值 |
|---|---|
| 触发 | 每天 03:00 |
| 模式 | 自动 · 自主度 可落盘 |
| 执行者 | 服务端 / 外部 harness |
| 存活上限 | 2 天 |

**入口**：`habitat tidy --apply` ｜ `POST /api/maintenance/tidy` ｜ UI：今天 · 管家

**步骤**：
1. 收集 doneAt ≥ 30 天的未归档任务
2. propose 一批 archive
3. commit（带反向操作）
4. 重扫

**产物**：归档变更集（可撤销）

**证据**：receipt.counts.archived；changeset id

**幂等**：已归档的不再进候选；同一批重复执行是空操作

**降级**：
- 没有调度器 → 只在 CLI / 今天页手动触发
- 没有模型 → 不受影响：这一步本来就不需要判断

**默认归属**：平台进程


### 4. `daily-brief` 每日简报

**目标**：每天一次，把今天 / 逾期 / 读一半 / 积压 / 欠账摆到人面前；陈述事实，不给建议。

| 项 | 值 |
|---|---|
| 触发 | 每天 08:00 |
| 模式 | 自动 · 自主度 只读 |
| 执行者 | 服务端 / 外部 harness |
| 存活上限 | 1.5 天 |

**入口**：`habitat brief` ｜ `GET /api/maintenance/brief` ｜ UI：今天页

**步骤**：
1. 收集今天的日程与到期任务
2. 扫逾期 / 读一半 / 积压
3. 算生命周期欠账与活性分布
4. 渲染同一份文本（CLI / 邮件 / 页面一致）

**产物**：简报文本；可选：一封邮件

**证据**：receipt.at；.habitat/state/brief.json（当天已发标记）

**幂等**：按天去重：同一天只发一次

**降级**：
- 没有邮件通道 → 只落 CLI / API，不发信；人打开今天页仍能看到同一份
- 没有调度器 → 打开今天页时现算，不保证每天主动出现

**默认归属**：平台进程


### 5. `reminders` 到点提醒

**目标**：快到点的日程提醒一次；逾期任务每天汇总一次，不逐条轰炸。

| 项 | 值 |
|---|---|
| 触发 | 每 1 分钟 |
| 模式 | 自动 · 自主度 有外发 |
| 执行者 | 服务端 / 外部 harness |
| 存活上限 | 2 小时 |

**入口**：`habitat notify --send` ｜ `POST /api/notify/run` ｜ UI：通知设置

**步骤**：
1. 找 30 分钟内开始的日程
2. 查 reminders.json 是否已提醒
3. 发信
4. 逾期任务每日汇总一次

**产物**：提醒邮件

**证据**：receipt.sent；.habitat/state/reminders.json

**幂等**：每条日程一次；逾期汇总每天一次

**降级**：
- 没有邮件通道 → 跳过并在回执里写 skipped，不假装发过
- 没有调度器 → 只能手动 notify --send

**默认归属**：平台进程


### 6. `rules` 规则通知

**目标**：结构化规则命中时落到站内通知；自由文本规则只登记、不执行。

| 项 | 值 |
|---|---|
| 触发 | 每 5 分钟 |
| 模式 | 自动 · 自主度 只读 |
| 执行者 | 服务端 / 外部 harness |
| 存活上限 | 3 小时 |

**入口**：`habitat rules run` ｜ `POST /api/rules/run` ｜ UI：AI · 自动化

**步骤**：
1. 加载启用的规则
2. 按 kind 求值（收件箱溢出 / 逾期 / 读一半）
3. 同规则同日去重
4. 写通知

**产物**：站内通知

**证据**：receipt.fired；.habitat/state/notifications.jsonl

**幂等**：每规则每天一次（notifications.jsonl 反查）

**降级**：
- 没有调度器 → 只能在自动化页点「运行一次」
- 没有模型 → 不受影响：只支持结构化规则，自由文本永远不执行

**默认归属**：平台进程

> custom 类型规则会明确 skip，不允许「看起来配了其实没跑」。


### 7. `index-rebuild` 索引重建

**目标**：索引坏了或换了机器时，从文件重建一份可丢弃的索引。

| 项 | 值 |
|---|---|
| 触发 | 修复动作，不参与存活判定 |
| 模式 | 自动 · 自主度 可写派生 |
| 执行者 | 服务端 / 人 |
| 存活上限 | 不做存活判定 |

**入口**：`habitat reindex` ｜ `POST /api/system/reindex` ｜ UI：系统 · 健康恢复

**步骤**：
1. 清空索引
2. 全量扫盘解析
3. 重建对象与倒排
4. 回报对象数与解析率

**产物**：新的 SQLite 索引

**证据**：/api/system → health.indexDocs

**幂等**：幂等：删掉重来结果一致

**降级**：无（不依赖外部条件）

**默认归属**：人

> 这是修复手段，不是闭环；列出来是为了让「删库重建」这条路径有据可查。


## 2.2 消化（4 条）

AI 的「判断 / 提炼 / 连接」三个切入点。服务端只备料，判断交给模型或人。

### 8. `triage-inbox` 收件箱分流（判断）

**目标**：收进来的碎片，判断它是什么、值不值得留、该归到哪、和谁重复。

| 项 | 值 |
|---|---|
| 触发 | 事件：新碎片进入收件箱，或每日一次 |
| 模式 | 备料 + 判断 · 自主度 只能提案 |
| 执行者 | 平台 Agent / 外部 harness / 人 |
| 存活上限 | 3 天 |
| 积压指标 | 收件箱条数 |

**入口**：`habitat next / habitat list --what inbox` ｜ `GET /api/inbox · GET /api/lifecycle` ｜ UI：收件箱

**步骤**：
1. 读收件箱条目与标签分布
2. 用检索找相似条目（确定性）
3. 判断：留 / 归 / 并 / 弃
4. 产出提案或衍生笔记

**产物**：标签 / 归属建议；去重建议；衍生笔记

**证据**：receipt.produced（note / changeset id）；journal: propose

**幂等**：同一条碎片不重复判：处理后在正文或提案里留痕

**降级**：
- 没有模型 → 只给去重与相似候选（BM25），不做语义归类
- 没有调度器 → 按需触发，积压数在 loops status 里可见

**默认归属**：外部 harness 或平台 Agent


### 9. `digest-source` 提炼（有衍生）

**目标**：把读过的章节压成自己的话，产出摘要 / 批注 / 衍生笔记，而不是收藏夹里多一条。

| 项 | 值 |
|---|---|
| 触发 | 事件：章节读完或产生批注后 |
| 模式 | 备料 + 判断 · 自主度 只能提案 |
| 执行者 | 平台 Agent / 外部 harness / 人 |
| 存活上限 | 7 天 |
| 积压指标 | 有 AI 切入点的欠账数 |

**入口**：`habitat next` ｜ `GET /api/lifecycle · POST /api/derive` ｜ UI：阅读器 · 衍生笔记

**步骤**：
1. 找「已入库 / 有衍生」但缺结论的章节
2. 读正文与既有批注
3. 压成 3-5 条自己的判断
4. propose 衍生笔记

**产物**：衍生笔记；批注

**证据**：receipt.produced；journal: derive / annotate

**幂等**：同一章节已有衍生则不再重复生成；追加要指明目标

**降级**：
- 没有模型 → 只列出「读完了但没有衍生」的清单
- 没有调度器 → 按需触发

**默认归属**：外部 harness 或平台 Agent


### 10. `connect-notes` 连接（双链建议）

**目标**：新写的笔记要和已有的连起来；没有入链的定稿等于埋在土里。

| 项 | 值 |
|---|---|
| 触发 | 事件：笔记成篇后，或每周一次 |
| 模式 | 备料 + 判断 · 自主度 只能提案 |
| 执行者 | 平台 Agent / 外部 harness / 人 |
| 存活上限 | 7 天 |
| 积压指标 | 有 AI 切入点的欠账数 |

**入口**：`habitat stuck --ai` ｜ `GET /api/lifecycle · GET /api/graph` ｜ UI：关系图

**步骤**：
1. 找已成篇但入链为 0 的笔记
2. 检索候选（同标签 / 词面相近）
3. 判断哪条是真关系
4. propose 双链

**产物**：双链建议 / 变更集

**证据**：receipt.produced；journal: propose

**幂等**：已建议过的组合不重复提；接受或拒绝都留痕

**降级**：
- 没有模型 → 只给候选列表，不判断关系强弱
- 没有调度器 → 按需触发

**默认归属**：外部 harness 或平台 Agent


### 11. `repair-links` 断链修复

**目标**：解析不到的 [[链接]] 要么补目标、要么改指向、要么明确删掉，不能一直挂着。

| 项 | 值 |
|---|---|
| 触发 | 事件：断链出现，或每周一次 |
| 模式 | 备料 + 判断 · 自主度 只能提案 |
| 执行者 | 平台 Agent / 外部 harness / 人 |
| 存活上限 | 7 天 |
| 积压指标 | 未解析链接数 |

**入口**：`habitat links` ｜ `GET /api/links/unresolved` ｜ UI：系统 · 健康

**步骤**：
1. 列出未解析目标与引用位置
2. 按标题 / 别名 / 拼写找候选
3. 判断补目标还是改指向
4. propose 修正

**产物**：断链清单；修正变更集

**证据**：receipt.counts.broken；journal

**幂等**：同一目标同一轮只报一次

**降级**：
- 没有模型 → 只给候选与位置，不做语义判断
- 没有调度器 → 按需触发

**默认归属**：平台 Agent 或人


## 2.3 判断（5 条）

翻新、复核、质疑、确认。共同点是**不允许自动改语义**，最多提案。

### 12. `renew-due` 翻新召回（该复核哪几条）

**目标**：把「该翻新了」变成「有证据可判」：服务端召回候选，agent 决定要不要推翻。

| 项 | 值 |
|---|---|
| 触发 | 每天 09:00 |
| 模式 | 备料 + 判断 · 自主度 只能提案 |
| 执行者 | 服务端 / 平台 Agent / 外部 harness |
| 存活上限 | 2 天 |
| 积压指标 | 到期复核数 |

**入口**：`habitat due · habitat renew <id>` ｜ `GET /api/renew/:id` ｜ UI：复盘

**步骤**：
1. 按间隔阶梯算到期
2. BM25 + 词袋 Jaccard 召回候选
3. 打包「它主张什么 + 哪几条可能撞上」
4. agent 判定 superseded 或 review --ok

**产物**：证据包；superseded 提案或复核记录

**证据**：receipt.counts.due；.habitat/state/review.json

**幂等**：同一对象同一档间隔只出现一次；review 后重新排期

**降级**：
- 没有模型 → 只出证据包，不下结论（这是设计：召回便宜、判定贵）
- 没有调度器 → 按需跑 habitat due

**默认归属**：服务端召回 + harness 判定

> 刻意一次只给 5 条：一次给几百条，人会直接关掉。


### 13. `review-interval` 复核节奏

**目标**：确认一条结论仍然成立后，把下次复核往后推一档；不成立就回到第一档。

| 项 | 值 |
|---|---|
| 触发 | 事件：复核某条之后 |
| 模式 | 人工确认 · 自主度 可写派生 |
| 执行者 | 人 / 平台 Agent |
| 存活上限 | 不做存活判定 |

**入口**：`habitat review <id> --ok|--stale` ｜ `POST /api/review/:id` ｜ UI：复盘

**步骤**：
1. 读当前档位
2. ok → 进一档（1/3/7/21/60/180 天）
3. stale → 回第 0 档，明天再看
4. 写 review.json

**产物**：下次复核时间

**证据**：.habitat/state/review.json；journal: review

**幂等**：每条每天最多记一次

**降级**：
- 没有模型 → 人自己判断，系统只记节奏
- 没有调度器 → 到期清单靠 habitat due 现算

**默认归属**：人 / Agent

> 不用 SM-2 的难度因子：固定阶梯更可预测，也不会掉进 ease hell。


### 14. `challenge-supersede` 质疑与取代

**目标**：旧结论撞上新证据时，提一条 supersededBy，让「过时」有据可查，而不是悄悄改掉。

| 项 | 值 |
|---|---|
| 触发 | 事件：翻新证据包显示真冲突 |
| 模式 | 人工确认 · 自主度 只能提案 |
| 执行者 | 平台 Agent / 外部 harness / 人 |
| 存活上限 | 不做存活判定 |

**入口**：`habitat renew <id> → habitat propose --ops …` ｜ `POST /api/proposals` ｜ UI：变更

**步骤**：
1. 读证据包
2. 判断是否真冲突（不是措辞不同）
3. 写 supersededBy 提案
4. 等人确认

**产物**：superseded 提案

**证据**：proposal id；changeset id

**幂等**：同一对 (旧,新) 只提一次

**降级**：
- 没有模型 → 只给候选，不提案
- 没有调度器 → 事件驱动，无到期概念

**默认归属**：Agent 提案 + 人确认

> 旧文永不删除；被取代是状态，不是消失。


### 15. `proposal-approve` 提案确认

**目标**：改语义的变更必须逐条被人看见：提案 → 四项校验 → 人确认 → 落盘 + 反向操作。

| 项 | 值 |
|---|---|
| 触发 | 事件：有 pending 提案 |
| 模式 | 人工确认 · 自主度 可落盘 |
| 执行者 | 人 / 平台 Agent |
| 存活上限 | 不做存活判定 |
| 积压指标 | 待确认提案数 |

**入口**：`habitat propose --ops … --commit（信任边界，见下）` ｜ `POST /api/proposals/:id/apply` ｜ UI：变更

**步骤**：
1. propose（带 base / inverse / 事件）
2. validate 四项校验
3. 人逐条确认
4. commit 落盘并重建索引

**产物**：变更集；事件；反向操作

**证据**：changeset id；journal: propose/commit

**幂等**：变更集只能提交一次；已提交的再 apply 返回冲突

**降级**：
- 没有模型 → 不适用：这一步是人的判断
- 没有调度器 → 事件驱动

**默认归属**：人

> CLI 的 --commit 是给受信 harness 的快捷方式，不是给模型的默认路径；平台侧必须在 UI 逐条确认。


### 16. `job-advance` 作业推进

**目标**：多步目标带检查点：中断能续，等待不是失败，失败有退避和上限。

| 项 | 值 |
|---|---|
| 触发 | 事件：有 queued / running 作业 |
| 模式 | 人工确认 · 自主度 可落盘 |
| 执行者 | 服务端 / 平台 Agent |
| 存活上限 | 不做存活判定 |
| 积压指标 | 未完成作业数 |

**入口**：`POST /api/jobs · POST /api/jobs/:id/advance` ｜ UI：AI · 作业

**步骤**：
1. 排队（幂等键去重）
2. 推进检查点
3. 第二步固定停在 waiting-approval
4. 失败按 30/60/120 秒退避，三次判永久失败

**产物**：作业状态与检查点

**证据**：.habitat/state/jobs.jsonl；journal

**幂等**：idempotencyKey 相同的作业不重复排队

**降级**：
- 没有调度器 → 只能由人或有 UI 的 Agent 推进
- 没有模型 → 作业本身不判断，判断在步骤实现里

**默认归属**：平台 Agent

> 当前没有 CLI / MCP 入口：外部 harness 只能走 HTTP。这是已知缺口，手册里标了。


## 2.4 交付（3 条）

进出与发布。前两个决定材料怎么进来、怎么备份；最后一个决定代码怎么上线。

### 17. `mail-ingest` 邮件入库

**目标**：发给自己的材料（附件 / 正文）进收件箱，不靠手动复制。

| 项 | 值 |
|---|---|
| 触发 | 每 15 分钟 |
| 模式 | 自动 · 自主度 可写派生 |
| 执行者 | 服务端 / 外部 harness |
| 存活上限 | 4 小时 |

**入口**：`habitat inbox-mail --fetch` ｜ `POST /api/inbox/mail` ｜ UI：收件箱 · 收信

**步骤**：
1. IMAP 拉取未读
2. 按 allowFrom 过滤
3. 解析正文与附件
4. 落到 inbox/

**产物**：收件箱条目

**证据**：receipt.counts.ingested；journal: ingest

**幂等**：按 Message-ID 去重（已入库的不再收）

**降级**：
- 没有邮件通道 → 跳过并记 skipped；不新建空条目
- 没有调度器 → 手动 --fetch

**默认归属**：平台进程或系统 cron


### 18. `export-backup` 导出校验

**目标**：定期导出一份带哈希清单的副本并校验，确保「文件是事实源」不是一句口号。

| 项 | 值 |
|---|---|
| 触发 | 每天 04:00 |
| 模式 | 只验证 · 自主度 只读 |
| 执行者 | 外部 harness / 人 |
| 存活上限 | 7 天 |

**入口**：`habitat export --out <目录> --verify`

**步骤**：
1. 原样复制文件与目录结构
2. 生成哈希清单
3. 按清单逐项校验
4. 回报对象数与解析率

**产物**：导出目录 + manifest

**证据**：receipt.counts.files/objects；manifest.json

**幂等**：导出到新目录；同目录重跑覆盖同名文件

**降级**：
- 没有调度器 → 手动导出；发布前必须做一次

**默认归属**：外部 harness / 人


### 19. `release-promote` 发布到生产

**目标**：tag → 构建 → 单测 → 重启 → 健康检查 → 对比对象数与解析率，任一项不过自动回滚。

| 项 | 值 |
|---|---|
| 触发 | 事件：打完 tag 后 |
| 模式 | 只验证 · 自主度 有外发 |
| 执行者 | 人 / 外部 harness |
| 存活上限 | 不做存活判定 |

**入口**：`node scripts/promote.mjs vX.Y.Z [--dry-run]` ｜ UI：无（命令行）

**步骤**：
1. 检查工作区干净
2. 记录基线
3. 切 tag / 装依赖 / 构建
4. 跑单测
5. 重启并探活
6. 对比对象数与解析率
7. 不过则回滚

**产物**：生产版本；健康检查报告

**证据**：promote 输出；/healthz；对象数 / 解析率对比

**幂等**：同一 tag 重复 promote 结果一致；失败自动回滚

**降级**：
- 没有 Shell / 生产目录 → 按 docs/workflow.md 人工执行，不能省健康检查

**默认归属**：人

> 平台进程不能执行它：需要生产目录、Shell 和重启权限。这是「外部 harness 才能接」的闭环样本。


## 3. 外部 harness 接入清单

按顺序回答七个问题，答不上来的那一项就是闭环会断的地方：

1. **它什么时候该跑？** 时区明确吗？存储用 UTC、显示用本地时间。
2. **它跑得完吗？** 单次超时多少？超过预算要大声失败，不能静默挂着。
3. **重复跑会怎样？** 每条闭环的「幂等」一栏写了答案；写不出来的不允许接。
4. **产物写在哪？** 产物必须是可指认的 id，不是「我改好了」。
5. **怎么证明它跑过？** 跑完必须 `habitat loops beat <id> --ok --produced …`；没有回执等于没跑。
6. **失败了谁接手？** 连续失败三次就停下来通知人，不要无限重试。
7. **它不能做什么？** 判断类闭环只许提案，不许 commit；外发类必须先过人。

### 一个最小可用的 cron 组合

```cron
# 每 15 分钟：把外部改动收进索引 + 收一次邮件
*/15 * * * * cd /path/to/habitat && npx habitat loops run watch-external --actor agent:cron
*/15 * * * * cd /path/to/habitat && npx habitat inbox-mail --fetch --actor agent:cron

# 每天 08:00：简报；09:00：翻新队列
0 8 * * *  cd /path/to/habitat && npx habitat loops run daily-brief --actor agent:cron
0 9 * * *  cd /path/to/habitat && npx habitat loops run renew-due --actor agent:cron

# 每周日 04:00：导出校验
0 4 * * 0  cd /path/to/habitat && npx habitat export --out /backup/habitat --verify
```

`--actor` 会写进回执，用来回答「这次是谁跑的」。没有它，回执只能记成 `agent:external`。

## 4. 故障排查

| 现象 | 先查 | 常见原因 |
|---|---|---|
| `down` 但进程活着 | `habitat loops status --json` 的 `lastAt` | 定时器被 `HABITAT_*_MS=0` 关了；或 harness 的 cron 被删了 |
| 两个执行器都跑了 | `loop-runs.jsonl` 里同一窗口两条 `ok` | 没有租约：只保留一个 owner，另一个改成 `--dry-run` |
| 跑完没有产物 | 回执的 `produced` 为空 | 闭环只做了「扫描」，没做「落盘」；回到步骤表看断在哪一步 |
| `blocked` 一直是邮件 | `habitat notify` 看缺哪个字段 | 没配 SMTP；补配置或把闭环标成 paused |
| 回执很多但没人看 | `backlog` 持续变大 | 闭环在「生产」，但没有人消费产物——这比不跑更糟 |

## 5. 怎么改这份手册

1. 改 `shared/loops.ts` 里的目录（新增 / 删除 / 改字段）。
2. `npm run test:unit`：契约测试会检查每条闭环都有入口、证据、幂等、降级。
3. `habitat loops manual --out docs/automation-manual.md` 重新生成。
4. 手册与代码在同一个 commit 里，评审时一起看。

> 反模式：直接手改这份 Markdown。下一次生成就会覆盖，且没人知道哪份是真的。
